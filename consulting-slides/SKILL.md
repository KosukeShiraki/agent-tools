# 戦略コンサルティング資料（HTMLスライド）

## 最重要方針

**「見た目を整える」のではなく「論理を視覚化する」。**
文章で説明せず、情報同士の関係性を図解として表現する。
箇条書きを箱で囲っただけのページを作らない。

各ページについて、レイアウトの前に必ずこの順で考える。

1. このページで伝えたい**結論**は何か
2. その結論を支える**論理構造**は何か（因果／比較／分類／順序／階層／変化のどれか）
3. その論理構造を最も自然に表現する**図解**は何か

図解は「足すものがなくなったとき」ではなく**「削れるものがなくなったとき」に完成する**。箱・矢印・ラベルのどれかを消しても結論が伝わるなら、それは削る（削除テスト：`references/quality.md`）。

## パスの読み方

以下で `<skill>` は、**この SKILL.md があるディレクトリ**を指す。プロジェクト配置なら `.claude/skills/consulting-slides`、ユーザー配置なら `~/.claude/skills/consulting-slides`。コマンドはどのカレントディレクトリから実行してもよい。

## 手順

### Step 0｜前提を確定する

次の5点を確定させる。ユーザーがテーマしか指定していない場合は、**質問で止めずに妥当な既定値を置いて進め、冒頭でその前提を明示する**。

| 項目 | 既定値の置き方 |
|---|---|
| テーマ | ユーザー指定をそのまま使う |
| 目的 | 「読後に何を判断・行動してほしいか」を1文で置く（例：限定領域でのパイロット承認） |
| 対象読者 | 指定がなければ経営層・部長クラス |
| 枚数 | 指定がなければ表紙＋本文9枚＝全10枚 |
| 出力先 | 指定がなければカレントディレクトリに `<テーマの英字スラッグ>-slides.html`（例：`shap-proposal-slides.html`） |

### Step 1｜ストーリーラインを設計し、先に提示する

ページを書き始める前に、全ページ分の**タイトル（＝結論）だけ**を先に並べて通しで読む。

- 前ページの結論が、次ページの問いになっているか
- 1ページに主張が複数混在していないか
- 「だから何なのか」が言えない分析ページがないか

**ストーリーラインは HTML を組む前に、最初の返答で表にして提示する。** 列は「ページ番号｜タイトル（結論）｜図解パターン#」の3つ。対話中ならユーザーの修正を受けてから組み、自律実行なら Step 0 の前提と一緒に提示してそのまま進める。論旨の差し替えは HTML を組んだ後より、この表の段階の方が桁違いに安い。

枚数別の標準構成（表紙を含む）：

| 枚数 | 構成 |
|---|---|
| **10枚（既定）** | 表紙 → サマリー（問い→答え）→ 現状の因果 → 課題分解 → 打ち手の原理 → 他選択肢との比較 → 前提の転換 → 実行プロセス → 限界と対応 → 意思決定の依頼 |
| 6枚（短縮版） | 表紙 → サマリー → 現状の因果 → 打ち手と他選択肢との比較 → 実行プロセス → 意思決定の依頼 |
| 15枚（詳細版） | 10枚版に、仮説検証（#14）・定量的な推移（#17）・構成比（#18）・シナリオ（#21）・体制（#23）のうち論旨に必要なものを、該当する位置に差し込む。増やす場合も「1ページ1主張」を崩さない |

枚数が表にない場合は最も近い構成を土台にし、削る・足す理由が言えるページだけを増減する。

### Step 2｜図解パターンを選ぶ

`references/layouts.md`（索引）を読み、各ページの論理構造に対応するパターンを**24種から1つ**選ぶ。決めたパターンの `references/patterns/NN-*.md` **だけ**を読む（全ファイルを読まない）。1ページに2つ以上のパターンを混ぜない。新しい構図を発明せず、最も近いパターンに寄せる。
**論理関係のない箱を横並びにしない。矢印は意味のある関係にのみ使う。**

索引にはパターンごとの**上限**（箱・行・要素の数）がある。内容が上限を超えるときは、文字を小さくして詰めるのではなく、ページを分けるか粒度を1段上げる。

位置関係には必ず意味を持たせる。
原因と結果＝左から右／階層＝上から下／対立＝左右／変化＝Before-After／分類＝2×2／工程＝横フロー／収束＝中央へ

### Step 3｜HTMLを組む

`<skill>/assets/template.html` を出力先にコピーして作業ファイルにする（複製元は必ず template。`example-deck.html` からは複製しない）。ページは必ず4層構造にする。

1. **タイトル**：左寄せ・太字。テーマではなく主張を書く。直下に細い横罫。
   - ×「現状分析」／○「現状の最大の課題は、個別最適による業務の複雑化にある」
2. **導入文**：2〜4行。背景・問題意識・前提。強調はキーワードのみ `<b>`。
3. **メイン図解**：`.fig` 内。ページの約70%を使う。
4. **Bottom Line**：最下部の帯。「つまり何が言えるか」を1文・太字。ここだけ読んでページの意味が通ること。

各ページの `.pn` に `NN / 全枚数` を、`.brand` に資料名を入れる（`render.py` が照合する）。

**CSSの扱い**：`<style>` 内の既存ルールとトークンは検証済みなので**書き換えない**。調整は要素の `style=""` による上書きか、`<style>` 末尾への**新しいクラスの追記**で行う。既存の短いクラス名（`row`・`bar`・`hd`・`op`・`on` など）を新しい構図で再利用しない。

**文字は縮めない**：各クラスの `font-size` は雛形の値が下限で、`style=""` で小さくして収めない。収まらないのは情報が多すぎる合図なので、削除テストで削るかページを分ける。1行に入る全角文字数の目安は「箱の内幅 ÷ フォントサイズ」（`references/layouts.md` 共通の注意）。

**折れ線・棒グラフ**は座標を手計算せず `<skill>/scripts/chart.py` で生成する（使い方は `patterns/17-time-series.md`）。

### Step 4｜画像で検証する（必須・省略しない）

```bash
python3 <skill>/scripts/render.py <deck.html>            # 全ページ
python3 <skill>/scripts/render.py <deck.html> --pages 3,5-7   # 直したページだけ再検証
```

- 全ページのPNGを**一時ディレクトリ**に出力し、次を自動検査する。1つでも出れば終了コード1。
  - `PAGE_OVERFLOW`／`FIG_OVERFLOW`：ページまたは図解領域の縦溢れ（図がタイトルや Bottom Line に重なる）
  - `SPILL`／`CLIP`：箱から文字がはみ出す・切れる
  - `BLEED`：右端からのはみ出し
  - `PN_MISMATCH`：ページ番号が位置や総数と合わない
- 出力されたPNGを Read ツールで**実際に目視し**、図解の位置関係・罫線の揃い・色の使い方を確認する（自動検査は「意味の崩れ」を検出できない）
- レイアウト崩れ、意味の通らない図、本文と図の矛盾を見つけたら直して再検証する
- 溢れの直し方の優先順位：情報を削る → 行間・パディングを詰める → ページを分ける。**文字を小さくするのは選択肢に入れない**

### Step 5｜納品する

- **納品物はHTMLファイル1つだけ。** 作業ファイルをそのまま完成物とし、パスを提示する
- Artifact公開・PDF出力・PNGの同梱は**行わない**（PNGは検証用の一時ファイルとして破棄する）
- **PPTX を明示的に求められたときだけ** `references/export-pptx.md` を読んで変換する。求められていないのに作らない
- 数値をサンプルで置いた場合は「実データに差し替えて使う」旨を明記する
- Step 1 で提示したストーリーラインから変えた点があれば、その旨を添える
- ブラウザで開けば表示され、ブラウザの印刷機能から16:9のまま紙・PDFに出せることを伝える
- フォントは Google Fonts から読み込む。オフライン環境では OS の日本語フォントに置き換わり、行送りがわずかに変わりうることを一言添える

## 配色（固定・変更しない）

意味に紐づけて使う。装飾として色を足さない。

| トークン | 値 | 意味 |
|---|---|---|
| `--navy` | `#12395b` | 論理構造。罫線・矢印・枠・上端バー・あるべき姿の側 |
| `--navy-d` | `#0b2740` | 見出し文字 |
| `--acc` | `#9a2b32` | **1ページ1〜2箇所のみ。** 問題・リスク・判断ポイント・推奨案 |
| `--navy-t` / `--fill` | `#eaf0f6` / `#f1f4f8` | 従属情報・推奨象限の地色 |
| `--ink` / `--ink2` / `--ink3` / `--ink4` | 濃→淡 | 本文の階層。最も薄い `--ink4`（`#64707c`）でも白地・淡色地で 4.5:1 以上を確保している。これより薄い文字色を `style=""` で足さない |

アクセントの標準的な置き場所：コアイシューの枠／推奨象限の枠／リスクを上げる要素／判断ゲート／Bottom Line帯の左ライン（全ページ共通）。

## 禁止事項

- 写真・イラスト・装飾アイコン・絵文字・グラデーション・影・立体表現・角丸の多用
- Webサイト風、インフォグラフィック風、広告風、PowerPointのSmartArt風の見た目
- 意味のない矢印、論理関係のない横並び、不要な分類、粒度の混在
- ボックス内に3行以上の文章（長い説明はボックス外に小さく置く）
- 固定サイズ（1280×720）と左右マージン52pxの崩し
- 収めるために文字を雛形より小さくすること

## 納品物はHTMLファイルのみ

PDF出力・Artifact公開・PNGの同梱は行わない。プロジェクト内に副産物のファイルを残さない。
検証用PNGは一時ディレクトリに出力し、目視確認が済んだら参照しない。PPTX は「pptx で」「パワポで」と明示されたときだけ、`references/export-pptx.md` の手順で HTML から変換する。

## スキル自体を修正したとき

雛形・パターン・スクリプトを変えたら、納品前ではなくその場で次を通す。

```bash
python3 <skill>/scripts/check_skill.py        # 索引↔パターンファイル↔カタログ、スニペットのクラス、3ファイルのCSS一致、SKILL.md のリンク
python3 <skill>/scripts/render.py --self-test  # 検出クラスがそれぞれ鳴り、正常ページで鳴らないこと
```

雛形の `<style>` は `assets/template.html`・`references/example-deck.html`・`references/pattern-catalog.html` の3か所で**同一**に保つ（`check_skill.py` が照合する）。
